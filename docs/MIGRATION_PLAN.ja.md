# 製品サイト移行計画

目的は、`reachmade.com` を親サイトとして維持しながら、現在の製品カタログ（現時点6件）の入口・本体・発信導線を製品単位で切り替えられる状態にすることです。既存URLを先に削除せず、1製品ずつ確認して進めます。

## フェーズ 0: 台帳を固定する

1. `src/products.mjs` の製品ID、リポジトリ、本体URL、Reachmade入口を変更せず記録する。
2. 各製品の所有者、ライセンス、問い合わせ先、利用開始手順を確認する。
3. 親サイト、製品本体、GitHub、SNSの成果を別の対象として計測する。
4. 移行前の基準URLを保存し、旧URLを削除しない。

完了条件: 台帳に登録した各製品について、現在URLと「目指すURL」が1行で説明できる。

## フェーズ 1: サブドメイン入口を安定させる

製品ごとに次の順で行います。

1. Cloudflareで対象サブドメインのDNS・Workerカスタムドメインを確認する。
2. HTTPSで入口が200または意図した302を返し、パスとクエリを保持することを確認する。
3. 本体URLが200で、製品名・デモ・GitHubのリンクが正しいことを確認する。
4. `www`や旧入口がある場合は、対応する製品ページへの301/302を設定する。
5. 入口を確認できた日時と、確認できなかった場合の理由を台帳に記録する。

現状では権威DNS（1.1.1.1）とCloudflare IPを指定したHTTPSで、台帳登録分（現時点6件）の入口を確認済みです。通常の名前解決で一部が解決できない場合は、端末やDNSリゾルバのキャッシュを切り分けます。DNS設定の削除・変更は行いません。

## フェーズ 2: 製品本体を移すか判断する

各製品を次の3状態に分類します。

| 状態 | 扱い |
|---|---|
| 既存本体を継続 | Reachmade入口から既存URLへ転送。まずこの状態で利用導線を測る |
| 製品サイトを新設 | サブドメイン側に製品の説明・デモ・利用手順を配置し、本体アプリは別URLでもよい |
| 本体も移転 | 認証、保存データ、外部連携、ライセンス、ロールバックを個別確認してから実施 |

最初の段階では「製品紹介サイト」と「アプリ本体」を同時に移しません。ブラウザ保存領域や認証がある製品は、旧オリジンのデータを自動で引き継げないためです。

## フェーズ 3: 導線と計測を製品別に接続する

1. 親サイトの製品カードから、対象製品のサブドメインまたは本体へ遷移する。
2. SNS・記事・動画は、内容に対応する製品ページへ直接誘導する。
3. UTMは親サイト、製品、媒体、投稿を区別できる命名にする。
4. CTAクリック、デモ開始、登録、ダウンロード、問い合わせを段階ごとに記録する。
5. 取得できない段階は「未確認」とし、登録やスターの増加を投稿の効果と断定しない。

## フェーズ 4: README・SNSのリンクを更新する

製品サイトの実測が完了した製品から、GitHub README、プロフィール、固定投稿、記事のリンクを更新します。更新前に旧URLから新URLへの対応を保存し、リンク切れを確認します。新しい投稿、返信、広告、課金は、この移行計画だけでは実行しません。

## フェーズ 5: 旧URLを維持したまま評価する

各製品の切り替え後、少なくとも次を確認してから旧入口の整理を判断します。

- 入口・製品本体・GitHubが連続して開ける
- CTAの遷移と計測値が取得できる
- 認証、保存、外部連携が壊れていない
- 問い合わせ先の所有者と受信が確認できる
- SNSやREADMEの既存リンクが新入口へ向いている

問題があれば、旧URLを残したままWorkerの転送先を戻します。DNSやドメインの削除、アプリデータの移行、ライセンス変更は別途承認を得てから行います。

## 優先順位

1. **通常DNSで解決できない場合のキャッシュ**を、別の外部ネットワークでも確認する。
2. **相談導線**の所有者・受信を確認し、Reachmade専用窓口にするか決める。
3. **製品別計測**を設定し、親サイトの閲覧と製品成果を分離する。
4. 入口が確認できた製品から、README・SNSのリンクを順番に更新する。

この順番なら、親サイトの公開を止めず、製品ごとの移行を個別にロールバックできます。
